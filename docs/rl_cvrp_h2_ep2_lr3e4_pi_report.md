# CVRP Local-Search RL Report: `rl_cvrp_h2_ep2_lr3e4`

Date: 2026-06-08

This experiment does not replace cuOpt with an RL solver. We keep cuOpt's
routing engine and insert a learned policy inside local search: whenever cuOpt
has to choose a node/operator subset to search, C++ proposes `K` candidate
subsets and the policy chooses one of them. The action space is therefore small
and cuOpt-defined, not an unconstrained route-generation problem.

## MDP and RL Formulation

One episode is one cuOpt CVRP solve. In this run, each training episode has a
2-second time limit. One RL decision happens at a cuOpt local-search callback.

At a decision point, the state contains the fixed problem features
(`coordinates`, `demand / capacity`), the current incumbent solution encoding,
the current objective value, and `K` candidate node/operator subset masks
generated by cuOpt. Each mask says which nodes are selected and which local
search operator produced the anchor signal:

| Mask bit | Operator |
| --- | --- |
| 1 | sliding |
| 2 | vrp |
| 4 | recycle_vrp |
| 8 | two_opt |

The action is to choose one candidate subset index:

```text
a_t in {0, ..., K-1}
```

cuOpt then executes local search on the real incumbent using the selected
subset. cuOpt only accepts improving moves, so cost-change labels are
non-negative; candidates without an accepted improving first step keep label 0.

The training objective is a full-feedback contextual-bandit objective, not a
Monte Carlo episode-return objective. For every state, C++ evaluates all `K`
candidates on copied solutions and returns labels for every arm:

```text
trail_rewards = [immediate_reward_0 ... immediate_reward_K-1,
                 lookahead_reward_0 ... lookahead_reward_K-1]
```

Training uses the lookahead half. For this run, `reward_horizon=2`, so the
target is the cost decrease after forcing a candidate for one step and then
continuing one more local-search step on the copied solution. Evaluation and
benchmark use `reward_horizon=1`; no future label is used for action selection.

The neural model scores all `K` arms. Scores are converted to a policy with:

```text
logits_i = score_sign * score_i / temperature
pi = softmax(logits)
adv_i = normalize(lookahead_reward_i over valid arms)
J = sum_i pi_i * adv_i
loss = -J - entropy_coef * entropy(pi)
```

During training the policy samples from `pi`. During normal eval it uses greedy
argmax; benchmark can also use softmax sampling with `--selection sample`.

## Architecture and Code Path

The implementation has a C++/Python split:

| Component | Role |
| --- | --- |
| `cpp/src/routing/local_search/local_search.cu` | Finds anchors, generates `K` candidate subsets, computes immediate/lookahead labels on copied solutions, calls the Python callback, then executes the returned subset on the real solution |
| `rl_callback.py` | Builds model inputs from cuOpt state and candidate masks; returns the selected mask; stores full-feedback labels during training |
| `rl_rollout.py` | Runs one cuOpt solve in one worker process on one GPU |
| `train_rl.py` | Master process: launches rollout workers, aggregates transitions, updates the policy, evaluates periodically, saves checkpoints |
| `benchmark_rl.py` | Runs random, greedy policy, epsilon-greedy policy, or softmax-sampling policy benchmarks |
| `run_train_cvrp.sh` | Reproducible launch script for this run |

The run log starts with the actual executed setup:

```text
[setup] gpus=[2, 3] master=cuda:1 batch_episodes=4 K=16
reward_horizon_train=2 reward_horizon_eval=1 update_epochs=2
eval_runs=8 time_limit=2.0
```

## Results

The random baseline is apples-to-apples: it receives the same `K` cuOpt
candidate subsets and chooses uniformly at random. Lower final cost is better.

| Question | Best observed setup | Result |
| --- | --- | --- |
| Did the policy learn to rank cuOpt candidates? | Best ranking metric at round 131 | `top1_lookahead = 0.2242` vs random `1/16 = 0.0625`, about `3.6x` random |
| Best training-time 2s final-cost eval | `best_policy.pt`, selected at round 82, `K=16`, greedy action selection | policy mean `35.9191`, random mean `36.2127`, gap `+0.81%`; policy min `35.6183` |
| Best training-time 2s minimum | round 120 periodic eval | policy min `35.5797`, policy mean `35.9874`, gap `+0.62%` |
| Latest completed checkpoint behavior | round 143 training record | `top1_lookahead = 0.1996`, `top1_current = 0.2377`, no eval at round 143 |
| Best 20s benchmark mean final cost | `policy_round143.pt`, `K=40`, softmax sampling | policy mean `34.8202`, random mean `34.9367`, gap `+0.33%`; policy min `34.5773` |
| Largest paired 20s benchmark gap | `policy_round2.pt`, `K=16`, softmax sampling | policy mean `34.8246`, random mean `34.9556`, gap `+0.38%`; policy min `34.5193` |

Additional benchmark context:

| Benchmark | Random mean | Policy setup | Policy mean | Gap |
| --- | ---: | --- | ---: | ---: |
| 10s, 16 runs | 35.3965 | epsilon-greedy policy | 35.3098 | +0.25% |
| 20s, `K=16`, 8 runs | 34.9556 | greedy selected policy | 34.9416 | +0.04% |
| 20s, `K=16`, 8 runs | 34.9556 | policy softmax sampling | 34.8871 | +0.20% |
| 20s, `K=40`, 8 runs | 34.9367 | greedy selected policy | 34.9445 | -0.02% |
| 20s, `K=40`, 8 runs | 34.9367 | policy softmax sampling | 34.8988 | +0.11% |

The main pattern is that the learned policy clearly improves the candidate
ranking metric, while end-to-end final-cost improvement is positive but small.
Softmax sampling is generally stronger than greedy argmax in the 20-second
benchmarks, suggesting that the learned distribution contains useful
information beyond only the highest-probability arm.

## Takeaway

This is evidence that an RL policy can learn a useful local-search
candidate-subset selector inside cuOpt. The policy is not yet a large
end-to-end solver improvement: best 2-second eval gain is about `0.81%`, and
best available 20-second benchmark gains are about `0.3% - 0.4%` in the
strongest sampling setups. The next useful experiment is a larger paired
benchmark for `policy_round143 + K=40 + sample` and `policy_round2 + K=16 +
sample`, plus a controlled comparison of `reward_horizon=1,2,3` under the same
compute budget.
